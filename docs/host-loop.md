# Explicit bounded host loop

`host` connects an existing handoff check to one real local tool invocation. It
never chooses a scientific question, generates research ideas, calls a model,
interprets `requested_actions` as permission, or promotes scientific validity.
Hermes/the researcher still chooses the next check and reviews the observation.
All reports retain `scientific_validity: not_assessed`, `publication: human-only`.

## Commands

Start with an existing `research.json` whose record is active, has `next_check`,
and is not in `human_review`. Preparation does **not** run a tool. It does read
and freeze the explicitly selected inputs, so only prepare paths you intend to
inspect; it is not an automatic evidence-reference crawler.

```sh
flyfishhep host prepare WORKSPACE --tool read-file --file notes.md
# Inspect the JSON manifest and copy its exact request_id to ID.
flyfishhep host execute WORKSPACE ID                 # refused: no grant
flyfishhep host execute WORKSPACE ID --allow-exec --scope read-file
flyfishhep host status WORKSPACE ID
flyfishhep host resume WORKSPACE ID                 # verify saved output only
flyfishhep host accept WORKSPACE ID                 # separate handoff write
```

Only these tools exist:

| Tool | Preparation | Execution |
| --- | --- | --- |
| `read-file` | `--tool read-file --file RELATIVE_PATH` | Bounded regular-file read; output includes exact base64 bytes and UTF-8 text when decodable |
| `audit-run` | `--tool audit-run --run EXACT_RUN_ID` | Exactly `runner.audit_project(root, run_id)`; no implicit latest-run selection |
| `python` | `--tool python` | Exactly `runner.run_project(root, True, expected_freeze_id=approved_freeze)`; requires an already-created matching `flyfishhep freeze WORKSPACE` |

For either runner tool, use `--allow-exec --scope audit-run` or
`--allow-exec --scope python` respectively. There is no shell, free-form argv,
provider, network, publication, or dynamic tool-registration option. Python uses
the existing project's reviewed executable contract, not code generated by host.

`execute --allow-exec --scope TOOL` is a **local, unauthenticated, one-attempt
grant** issued explicitly by the caller. It binds the exact request ID, tool,
timeout, and attempt budget. It is not a signature, identity proof, reusable
permission, nor a permission derived from handoff contents. `--timeout` defaults
to 30 seconds at prepare; if supplied at execute it must equal the prepared value.
`--attempt-max` must be exactly 1. Invalid/boolean budgets in the Python API,
timeouts outside integer 1–300 seconds, tool/parameter mismatches, and broader
scopes are refused before a new invocation. Inspecting a completed result needs
no new grant and never calls the tool again.

## Request binding and storage

`.flyfishhep/host/REQUEST_ID/` contains:

- `manifest.json`: canonical-hash request identity, absolute workspace,
  `basis_revision`, exact `next_check`, tool/parameters, input-byte hashes,
  timeout/attempt budget, and runner-source hashes for runner tools;
- `input.json` for read-file: frozen exact bytes encoded as base64, hash-bound
  into the manifest. Runner inputs are bound to the existing frozen input packet;
  audit requests additionally bind the exact existing run packet;
- `state.json`: checksummed state envelope, attempts and exact issued grant;
- after completion, `output.json` and `receipt.json`: output hash/reference,
  grant, and hashed inventories of any linked run/freeze packets;
- after acceptance, the exact accepted handoff revision in state.

The manifest hash is the request ID, so identical preparation of the same
revision/tool/inputs/budgets reuses the request. Input changes, any handoff
revision change, a stopped handoff, suspended project, a missing/mismatching
freeze, or changed runner implementation prevent a new execution. The adapter
never silently freezes updated Python inputs. For Python dispatch the host passes
`manifest.inputs.freeze_id` as `expected_freeze_id`. The runner compares that
approval with its own selected, validated frozen packet before creating any run
directory, copying inputs, or launching a subprocess; its command and workspace
come from that same packet. A change after host prechecks therefore cannot launch
a different freeze. A caught refusal after the durable grant leaves `unknown`
with one attempt and manual review, not an automatic retry. Standalone
`run_project(root, allow_exec=False, expected_freeze_id=None)` keeps its previous
behavior when no expected freeze is supplied. Runner-source hashes are computed
from the current package sources, so this implementation change also changes
request identity; previously prepared requests are not silently upgraded.
Audit preparation deliberately
requires a valid, active, currently matching frozen project as well as the
selected historical run; it is stricter than the standalone historical audit.

All paths reject traversal and symlinks, including workspace ancestors and host
storage ancestors. Reads require regular files; final-component opens use
`O_NOFOLLOW`/`O_NONBLOCK` where available. Host writes use an exclusive workspace
host lock, same-directory atomic replacement, file fsync and POSIX directory
fsync. A lock is removed only when its inode is still the acquired inode. Locks
are never timed out, stolen, or automatically removed.

Bounds: read-file input ≤256 KiB; other inspected files and each host JSON
≤2 MiB; inspected trees ≤512 entries and ≤16 MiB total bytes each. The read-file
limit reserves space for JSON escaping/base64. Oversized runner output cannot be
claimed complete: it leaves an uncertain host attempt requiring manual review.
Read/audit operation deadlines require POSIX timers on the main thread; other
platforms/threads or an already-active process alarm are refused rather than
silently running without that deadline. Python execution uses the existing
runner's subprocess timeout, which must not exceed the host timeout. Freeze/hash
preflight and receipt persistence are bounded by input sizes, not a hard total
wall-clock deadline.

## Recovery and acceptance

State transitions:

```text
prepared --explicit grant--> running --> completed --explicit accept--> accepted
                                  \--> unknown (caught failure)
```

`running` is durably written **before** invocation, with the handoff writer lock
held for the final revision/state check. A later handoff update does not revoke
an already-authorized running attempt; acceptance still checks the latest state.
Process death can leave
`running` and an exclusive stale lock; caught failures leave `unknown`. Neither
state is retried, even if files suggest that the runner may have finished.
Investigate the process, runner receipts and side effects manually. Only an
operator who has confirmed the owner is gone may remove its stale lock; this
does **not** make `running`/`unknown` executable. `status`/`resume` then report
`recovery: manual_review`. There is intentionally no reset/retry/force/override
command. `resume` verifies already-completed output; it does not execute or
accept anything automatically.

Completed repeated `execute`, `status`, `resume`, and `accept` verify manifest,
frozen read snapshot, state, receipt, output and linked packet hashes. They do
not repeat the tool. A changed output or linked artifact is a refusal, not a
new result.

`accept` adds a standard four-field `note` (read-file) or `run` evidence reference
and an observation bound to the original `basis_revision`. Its summary identifies
the actual output SHA-256; the host receipt retains full byte provenance. This
is a report of execution, not scientific validation or a claim that handoff's
reported evidence became authenticated. Optional evidence binding can be added
later using the evidence commands; host does not depend on that schema.

Acceptance uses the latest handoff base for compare-and-update and refuses a
newer record, changed plan, suspension or human-review decision instead of
overwriting it. If the handoff write succeeded but the host's accepted-state
write failed, replay recognizes the exact existing evidence/observation entry
whose parent is the original basis. It repairs only host state and appends no
second history entry, including when a later record is suspended or under human
review. This reconciles an already-committed acceptance; it does not authorize a
new acceptance into a stopped record. A concurrent handoff writer causes a stale-base refusal.

## Integration API and limits

`hostloop.register_cli(commands)` attaches to existing argparse subparsers.
For `args.command == 'host'`, call `hostloop.dispatch(args)` inside the CLI's
existing JSON/error boundary. It returns JSON-compatible data and raises
`ContractError`/`OSError` for refusal. Direct APIs are `prepare`, `execute`,
`status`, `resume`, and `accept`; dispatch does not print or choose exit codes.

This is at-most-once dispatch for a retained request, **not** distributed
exactly-once side effects. Local hashes detect inconsistent edits, not an owner
who rewrites the entire manifest/state/receipt history. It assumes a trusted
local workspace: ancestor checks are not a hostile-filesystem race-proof
sandbox. Reviewed Python remains ordinary executable Python with the existing
runner's privileges; neither network denial nor resource isolation is enforced
by the OS here. The adapter itself has no network/model/provider capability,
but explicit Python approval still requires source review. Runner subprocess
timeouts are not an OS disk/memory/process quota. Do not approve untrusted code.
